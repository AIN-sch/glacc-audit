给梨加速器 任务中心 业务逻辑问题报告

提交日期：2026-10-26
涉及版本：1.26.10.1（Android，包名 com.geilijiasu.glacc）
涉及接口：game-xacc.xunlei.com


一、问题概述

任务中心的激励任务，在领取奖励时，服务端没有校验任务的前置状态是否已经满足。请求参数本身合法，就会发奖。

对于「看广告得时长」这一类的任务，前置状态本应是「广告完成」。实际情况下，这个前置状态缺失时，接口仍然返回成功，并且奖励真实入账。

需要强调的是，这不是端上的显示问题。用独立的钱包接口核对过，积分与剩余加速时长都实际增长。


二、正常流程与实际观测

按设计，一个激励任务的完整链路应当包含以下环节：

  1. 拉取任务列表
  2. 用户点击领取
  3. 客户端调起广告 SDK
  4. SDK 回调完成
  5. 客户端上报完成事件
  6. 调用领奖接口
  7. 服务端核对第 5 步的记录，发奖

实际观测到的情况是：省去中间环节之后，第 6 步依然返回成功（code: 0，rewardStatus: success），奖励照常入账。

第 7 步的核对，在「按子任务领取」这个分支上不存在。


三、涉及接口

3.1 任务列表

  GET /xlppc.gacs/api/gxsdn/act/advert/mobileGLTaskList?appid=8

响应顶层需要两个字段：

  data.snapshotId     任务快照 ID，UUID 格式
  data.strategyId     策略 ID，整数

子任务位于 data.list[].taskDetailList[]，取其中的 masterTaskId 与 taskId。

3.2 领奖

  POST /xlppc.gacs/api/gxsdn/act/advert/mobileTaskSpark/claim

请求体：

  {
    "action": "subtask_return",
    "masterTaskId": 52,
    "taskId": 222,
    "requestId": "1792984791513",
    "snapshotId": "&lt;上一步取得&gt;",
    "strategyId": 23
  }

响应：

  {
    "code": 0,
    "result": "ok",
    "data": {
      "orderId": "mt:spark:bd3e432ea9d08301a94640e74db44ac87f0bf20f",
      "rewardStatus": "success",
      "rewardMinutes": 1,
      "rewardCoin": 80,
      "alreadyClaimed": false,
      "rewardedAt": 1792984791
    }
  }

3.3 资产核对

  GET /xlppc.gacs/api/gxsdn/gold/get_user_wallet

这个接口与领奖链路独立，用它的返回值前后对比，才能确认奖励是否真的入账。


四、实测数据

同一账号，连续 11 个带 advertLink 字段的子任务，全部返回 code: 0。

  项目                          观测前        观测后        变化
  score（积分）                319600        320480        +880
  remain_acc_second（秒）      239700        240360        +660

每次返回 rewardMinutes: 1，rewardCoin: 80，orderId 前缀为 mt:spark:。

整个过程未调起广告 SDK，未发起任何广告相关请求。


五、服务端行为观察

以下几个细节对定位有帮助。

5.1 snapshotId 是一次性的

领奖成功之后，用同一个 snapshotId 再次请求，返回：

  code: 10053，请求无效，请检查参数

说明防重放机制是存在的，工作正常，但作用范围只到快照这一层。

5.2 不同 action 走不同分支

对同一组参数，更换 action 字段的取值，返回结果差异明显：

  action              返回码
  subtask_return      0
  master_expand       10053
  subtask_finish      10000
  task_finish         10000
  claim               10000
  finish              10000

服务端对这个接口的 action 有明确的分支处理，不是统一逻辑。问题集中在 subtask_return 这个分支上，其它分支的行为是正常的。

5.3 advertLink 为空的子任务无法领取

任务列表中 advertLink 字段为空的子任务（例如「愉悦赚」下的若干条），直接请求领奖接口返回 10053。这说明这类任务有另一套判定，本次问题未覆盖到这部分。

5.4 签名密钥硬编码在客户端

完成事件上报接口 mobileGLTaskPush 的请求体带有 sign 字段，算法为：参数按键名排序后拼接，末尾附加一个固定密钥，取 MD5 小写。

该固定密钥以字符串常量形式写在 index.android.bundle 中，反编译该 bundle 即可直接读取。相关代码形如：

  r1 = '&lt;19 位十六进制&gt;';
  var _closure1_slot8 = r1;

密钥放在客户端，等同于公开。


六、建议的处理方向

按优先级排列。

6.1 发奖前校验广告平台回传（最关键）

在 mobileTaskSpark/claim 处理 subtask_return 时，按设备标识、广告位 ID、时间窗口，向广告平台或本地回传日志查询是否存在对应的激励完成记录。查不到则拒绝发奖。

这一条能从根本上堵住问题。

6.2 改为一次性票据机制

广告 SDK 回调后，由服务端签发一张短时效票据，内容包含广告位、时间戳、设备标识。领奖请求必须携带该票据，服务端消费后作废。

这样在协议层就不存在「无前置状态也能领奖」的路径。

6.3 校验时间间隔

记录用户进入任务页的时间点，领奖时校验间隔不低于合理观看时长。激励视频通常 15 到 30 秒，间隔异常的直接拒绝并标记。

6.4 设备与账号维度的频次控制

对同一设备、同一账号的领奖行为做频次限制，并关注「连续多个任务的间隔高度一致」这类机器特征。

6.5 迁移客户端密钥

6.1 提到的事，建议一并处理。

6.6 回溯排查

排查历史发奖记录中缺少对应广告回传的部分，评估已产生的影响范围。
